The remaining classic 1,000-call failures are best attributed to a compiler execution-stack limitation in recursive expression traversal. The evidence now supports that attribution substantially more strongly than the original library-free controls did. It does not establish that every possible library declaration arrangement must fail, and it does not turn the failing original cases into accepted cases. I found no evidence-backed, compatible library type reformulation to recommend for this remaining failure.

This was a bounded, read-only review of local evidence and the unmodified TypeScript 6.0.3 implementation. I ran no compilation, changed no production source or git state, and performed no publication. The reviewed checkout was `/tmp/di-bag-replacement-spike`, clean HEAD `c9f8c181c53116c27c5411389af19773f5e802a6`; the official measurement source is `59d10c6c8ac13d63171f9f39c170da048d7e208c`. The installed compiler SHA-256 is `569177652966bd528c319171c7dd22860dbf72bde116cbc4f644f1d02bb12e39`, matching the instrumentation identity's original compiler hash.

The [official 40-case summary](original/summary.json) records 34 accepted outcomes and six failures. The failures are classic 1,000-call chained and replacement forms, each with valid, missing, and wrong-shape scenarios. They terminate with `RangeError: Maximum call stack size exceeded`; they are neither normal negative diagnostics nor TS2589. Native 7.0.2 completes all original 1,000-form positive and negative scenarios. Classic completes the original 1,000 bindings and modules scenarios. The original valid classic modules result remains a measured pass with limited headroom: 53.561 seconds of compiler time, 54.052 seconds for the total process, and 2,984 MiB reported peak RSS. These facts support a specific remaining limitation, rather than a blanket statement that classic cannot handle 1,000 registrations.

I independently compared the root-any snapshots with production: `types.ts`, `provider.ts`, and `module-types.ts` are identical; `di-bag.ts` differs only in the exported `DiBag` annotation documented by [its identity file](probes/root-any-ablation-identity.json). The unchanged generated-source identities are also retained by the diagnostic harness.

The subsequently captured extended authentic stacks provide direct evidence of the common mechanism. [Baseline chained](probes/full-stack-final-baseline-chained.stderr.log) has a repeated ten-frame expression-checking cycle with 9,980 additional duplicate lines; [baseline replacement](probes/full-stack-final-baseline-replacement.stderr.log) has 9,990. The corresponding root-any controls show 9,990 and 10,000 additional duplicate lines. Thus the original typed cases and the untyped facade control both retain roughly 1,000 nested receiver/call cycles when they fail. Increasing the captured error-stack length did not increase the execution stack, and these diagnostic reruns remain separate from the official acceptance rows. The [corrected derived comparison](probes/full-stack-comparison.json) expands the collapsed lines and reports 10,079 named frames for each baseline case and 10,049/10,059 for the root-any cases, excluding anonymous frames. The earlier visible-only counts are retained separately; values such as 59 count printed lines after duplicate-frame collapsing and are not execution-stack depths.

This matches the [unmodified checker](compiler-excerpts.txt). `resolveCallExpression` checks `node.expression` before resolving the call. Ordinary property access, at line 79704, checks its receiver via `checkNonNullExpression`. Repeating `.add(...)` or `.replace(...)` therefore descends the entire receiver chain while retaining the outer calls' checking frames. The typed baseline then requests a parameter type through `hasCorrectArity` and `getMinArgumentCount`, which tests whether trailing parameters accept `void`. That is why a private admission map appears at the top of the typed failure. It is work performed after the compiler has already accumulated the deep receiver stack; its appearance there does not establish an independent 1,000-registration recursion in that map.

The root-any branch takes `resolveUntypedCall` at line 81652 before typed overload resolution. That branch still checks ordinary argument expressions and returns `anySignature`. It demonstrates why merely bypassing the expensive arity/constraint path cannot be considered a complete explanation or fix. Likewise, the binder's ordinary call and property-access handlers at lines 48334 and 48341 delegate recursively to `bindEachChild`, explaining why the smaller imported program can encounter a related expression-depth limit in a different phase. The evidence does not isolate the precise reason that the altered program reaches a different stack threshold, so no JIT or initialization-order cause should be asserted as established.

My one concrete architectural direction is an upstream compiler change that processes long ordinary call/property-access receiver chains with an explicit continuation stack instead of one JavaScript call-stack layer per checking step. Descent would record the pending call and property-access operations; unwinding would perform the existing lookup, argument checking, contextual inference, overload selection, and result propagation in their existing order. The same traversal architecture needs to account for the binder's recursive treatment of this syntax, since the imported controls expose that earlier phase as well. This targets the repeated frames directly while preserving the library declarations and generated expression.

That direction is a hypothesis requiring compiler engineering and compatibility validation, not a proposed patch or a demonstrated pass. Continuations must preserve check modes, contextual typing, flow state, and cache/re-entrancy behavior; a separate eager pass over inner calls would not by itself establish that equivalence. It would leave `Entries`, `Provided`, `Bag.resolve`, token admission, optional properties, deferred generic assignments, and reflected method inference untouched, avoiding the public regressions exposed by earlier type-only candidates. It also preserves the original source and execution-stack setting. A change in a disposable compiler copy would remain diagnostic until an authorized, validated compiler version change was part of the actual supported configuration.

The current evidence is sufficient to report an unresolved upstream classic compiler stack limitation and to stop treating admission or registration-history micro-optimizations as an evidence-backed route to this particular 1,000-call target. It is not sufficient to claim universal impossibility, a fixed classic target, or completion of a requirement that explicitly includes those six failing original outcomes. The publication approval gate is outside this review and was not acted on.

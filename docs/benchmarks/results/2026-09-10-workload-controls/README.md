## Startup: a justified intermediate bound

Each route selects the same 96 asynchronous providers in the same order. Each provider allocates an application-owned 32,768-element numeric workspace and returns an externally resolved promise, released by a 4 ms timer. Every route makes exactly 96 factory calls, reaches 96 ready services, and disposes 96 values. The probe counts active factories directly, tracks externally rooted requests, and checks complete release. The named bound is selected readiness workers; dependencies inside a selected provider may still fan out.

The observed heap peak is sampled without forcing GC inside provider admission and includes unreachable allocations and runtime overhead. It is not the live application workspace bound. Baseline/post-close heaps are separately measured after GC in the logs. The arithmetic workspace estimate assumes eight-byte numeric array elements; counts are the deterministic resource oracle. A bound of eight offers a useful resource/latency tradeoff without changing the default.

Implementation accepts positive safe integers in `StartupOptions.concurrency`, retains default parallel eager scheduling, and routes `sequential` and numeric `1` through the same worker. Workers wait for acquisition readiness, never assimilating the exposed value. A shared failure flag stops other workers before rollback waits; existing cancellation checks stop selection admission. Started ownership remains with the closing runtime. Validation occurs before any factories. Numeric options retain one-time snapshotting, duplicate selections and lifetime behavior. No public helper or additional scheduler configuration was added.

## Observers: bounded production is an application responsibility

The identical transient raw acquisition burst has no observer, a fast synchronous observer, or an observer whose callback returns a promise held behind a real external gate. Counts 1,000 and 10,000 expose scaling comfortably inside the worker limits. No callback runs during the synchronous burst. The microtask drain delivers exactly 2N acquisition events in started/ready order. For pending callbacks, it starts all 2N callbacks without blocking production. External gates remain reachable until explicitly resolved/rejected; these are not unrooted never-settling promises.

For classic before at N=10,000, after-GC heaps are 8.81 MB during the no-observer burst, 13.99 MB during either observed burst, 9.00 MB after fast delivery, and 31.42 MB after pending delivery. Resolving/rejecting all external gates returns the pending case to 9.08 MB with zero pending callbacks and exactly 200 reported failures in rejection order. N=1,000 shows the same shape (pending drain 7.63 MB versus fast 5.38 MB). The after builds and native emitter reproduce the counts and retention shape.

The synchronous burst delta includes library queued event metadata. The pending-vs-fast drain delta includes application gate bookkeeping, promises and library rejection reporting closures retaining each original event; it cannot be attributed entirely to library queue retention. The base compact acquisition records and the probe's event-kind log also remain live. After the drain, the library delivery batch is detached; it is the externally pending callback work that sustains the additional retention. Existing event ordering/failure association is valuable and compatible. Lossless non-gating production cannot guarantee finite retention with an indefinitely slower consumer. No silent dropping, hidden cap or observer API change was made. Documentation now tells applications to keep callbacks small and control production or batch their work explicitly. The emitted regression additionally checks two observers' registration order.

## Close: limit the application wait, preserve cleanup

Each worker owns a pending native source and a pending disposer behind two independently released gates. A fulfilled control closes normally. In pending/failure controls, a 5 ms host deadline wins first while the source is pending (zero disposals), then while the disposer is pending (one disposal). The original close promise stays pending and identical across repeated `close()` calls. Observed waits are recorded, approximately 5–6 ms; no timing threshold is used in CI. Releasing both gates completes exactly one disposal and either success or the exact expected cleanup error. Both emitters and both source versions preserve this behavior.

The API cannot forcibly settle arbitrary user work. `Promise.race` already lets a host stop waiting without abandoning ownership, and startup cancellation already exposes the same eventual cleanup promise. Server guidance now demonstrates racing a handled close outcome with a host deadline and observing the eventual result. No close deadline that falsely reports released resources, cancellation helper or extra public API was added. The emitted regression uses a deterministic deadline gate.

## Declared dependency routing feasibility

The bounded investigation is complete; arbitrary-depth support was not implemented or claimed. `declared-probe.mjs` cold-resolves required-token raw `fromTokens` chains in fresh Node workers. Both emitters pass depths 100 and 500 with each callback called exactly once. Both depth-1,000 observations fail with `RangeError: Maximum call stack size exceeded` before any callback runs; both nonzero statuses and stacks are retained. This is a separate adapter path from the already fixed 1,000 raw/automatic *named proxy factory* regressions, which still pass in emitted tests. The positional adapter adds `Array.map` / `Reflect.get` frames before recursive acquisition.

Concrete source boundaries:

- `provider.ts:fromTokens` and `composition.ts:fromFunction/fromClass` authenticate and snapshot positional references, then close over their ordered slots in a `create(deps)` wrapper. `provider-operations.ts` retains references, keys, acquisition mode, contextual marker and pipeline operations, but the runtime only invokes the wrapper as a complete synchronous source.
- `acquisition-context.ts:withContext` takes an arbitrary named-dependency callback and passes its owner's context; it has no declared dependency tuple to prewalk. Plugins also retain positional references but perform source/validation/ownership operations, so references alone do not authorize source replay.
- `acquisition.ts:resolveBinding` canonicalizes aliases and owners, checks strict-root captures and cycles, publishes the consumer attempt/cache, records its incoming edge, constructs the proxy, emits acquisition-started, and enters family construction before calling `create`. Returned values then pass through source publication, mode classification and projection execution.
- The proxy consumes each transient exposed value once. Optional references resolve only if present; lazy references create closures that record edges only on invocation; all references resolve contributions in order and return a fresh frozen array. Late closure admission is tied to the source attempt and its owner, including closing behavior.

A smaller prewalk-before-resolve experiment is concretely incompatible. The normal mixed tuple `[optional(absent), transient, lazy(transient), transient]` yields `[1,2]` with two acquisitions before the lazy call, then three total; disposal order is `[3,2,1]` and consumer-start precedes dependencies. Prewalking the token once first yields `[2,3]`, four total calls/disposals, and a dependency-start before the consumer. Logs retain both controls for both emitters. Even caching prewalk values would need position-specific transient handoff and the original consumer edge/owner context; warming the normal cache is insufficient. Prewalking lazy/all keys indiscriminately would additionally break laziness or contribution order.

A compatible specialized route appears feasible as an internal follow-up: open the consumer attempt first, suspend it in an explicit acquisition frame, and evaluate authenticated reference slots in order using the original read/owner/alias rules. Each frame must retain its next argument position and exact values, hand transient outputs to the original slot once, leave lazy slots as original-attempt closures, and resume the source wrapper exactly once with those already-computed slots. An explicit stack would push required dependencies until an exposed value is available, not await native values merely to create callback arguments. Source publication and remaining projection execution must then occur once through the existing `ProviderExecution` path, with matching failure unwind, event order and context. A required-only first route could fall back for unsupported source forms, but it still requires splitting attempt initialization/invocation/completion and preserving nested ownership and construction-stack semantics. No generic callback replay or synchronous-to-async conversion is compatible. This is a concrete architectural boundary for future design, not a reason to claim all token depths fixed.

# How the tests assert on errors (measured by the controller at the 0.4.0 source, 2026-09-21)

- The tests assert mostly on MESSAGE TEXT, not on codes: 385 `toThrow(...)` assertions carry a string or a regex (339 strings, 46 regexes), against 15 `.code` assertions and 83 mentions of a `DI_BAG_` code in any form, in 21 test files. A string argument matches a substring of the message.
- Nothing automated finds or fixes these when a message is reworded: the compiler cannot see into a string and the codemod does not touch arbitrary strings. They surface as test failures. A failing message assertion after your phase rewords that message is an expected consequence to update; a failing assertion on a message your phase did NOT touch is a behavior change to report.
- The scale is small. About 44 of the 385 quote a word the program retires, and 31 of those are two phrases: `'bag is closing'` (10) and `'bag is closed'` (5), owned by phase 6; `'root lifetime cannot capture scoped...'` (16, in three spellings, two of them regexes), owned by phase 9. The rest are a handful per phase (`fromSyncFactory`, `fromAsyncFactory`, `acquisitionMode`, `buildAndStart`, `cleanup`, `startupOrder`, `createScope`, `alias`).
- Your plan must list the exact assertion strings your phase breaks, found with `grep -rhoE "toThrow\((/|['\`])[^)]*" tests | grep -iE "\b(word1|word2)\b" | sort | uniq -c`, and give the replacement for each. Use word boundaries: without them `register` matches `registration`, `scope` matches `scoped`, and `bag` matches the package name `di-bag`, all of which stay.

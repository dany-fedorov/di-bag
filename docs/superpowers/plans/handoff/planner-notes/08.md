# Scope notes: phase 7, plan file `docs/superpowers/plans/2026-09-21-08-requirement-renaming.md`, spike S6

State on entry: phases 0 to 6 done. `module.withRenamedExport({ currentExportKey, newExportKey })` exists; modules are installed with `builder.withInstalledModules([...])`; sealed with `buildModule({ exportedServiceKeys, moduleLabel? })`.

Add `module.withRenamedRequirement({ currentRequirementKey, newRequirementKey })`, the twin of `withRenamedExport`, returning a new module value. String service keys only; tokens cannot be renamed.
- Runtime: read `src/module.ts` closely. `ModuleDescription` holds `graph`, `exports` (public slot to local name) and `label`. `moduleGraph()` resolves names lexically: a binding's own local names, then the module's public names, then the installing host's public slots (`remap` returns the ref unchanged when the key is not in `scopeNames`). A requirement rename is a map from the local requirement name to the host name, applied in that last step, and it must compose through nesting: a module installed inside another builder that is then sealed passes its renamed requirement outward under the new name, and an outer `withRenamedRequirement` can rename it again. Factory parameter names never change. Decide the runtime errors for: unknown requirement, new name equal to an export of the same module, new name equal to another requirement. Use the final 0.5.0 codes for this NEW call (`DI_BAG_UNKNOWN_SERVICE_KEY`, `DI_BAG_DUPLICATE_SERVICE_KEY`) and add their sections to `docs/agent/errors.md` now; phase 11 maps the old codes onto them later.
- Types: `Module<P, R, C, D>` in `src/module.ts`; `R` is the required services; the constraint parameter `C` (`NeedConstraint` in `src/module-types.ts`) and the lifetime obligations in `src/lifetime-types.ts` mention requirement names. Study `Renamed`, `RenamedConstraints`, `RenamedProviders`, `RenameKeys`, `RenamedObligation` for exports and build the requirement twins. Negative cases with exact `Unsatisfied` messages: unknown requirement, collision, renaming to a name whose host service has the wrong shape (must be rejected at the host's build, with the consumer named).
- Tests (complete code): two modules that both require `config` with different shapes installed in one host; a renamed requirement satisfied by another module's export; nesting and re-renaming; a contribution inside a module whose factory uses the renamed requirement; `serviceSnapshot`/labels unchanged; type fixtures positive and negative, and a consumer fixture that checks declaration emit like the neighbours in `tests/types.test.ts`.

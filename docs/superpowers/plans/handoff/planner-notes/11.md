State on entry: phases 0 to 9 done. Lifetime values are `'singleton:one-per-container-tree'`, `'scoped:one-per-container'`, `'transient:one-per-resolve'`; decorators are provider methods (or the recorded fallback); the DEFAULT lifetime is still scoped.

1. Flip the default to `'singleton:one-per-container-tree'`. Run time: the default policy in `sourceDescription` (`src/provider-operations.ts`). Types: today an absent `lifetime` in a provider's graph contract means scoped (`LifetimeGraph` in `src/lifetime.ts` omits the key for scoped; `CanonicalLifetime`, `CheckedLifetimes`, `CheckedScopeLifetimes`, `Reach`, `LifetimeObligation`, `SealedLifetimes`, `SealAdmission` in `src/lifetime-types.ts` read it). After the flip an absent lifetime means singleton and scoped is explicit. The capture check then concerns every unmarked provider, so it needs a fast path: a graph with no scoped service cannot capture anything. Prototype and measure (S8). Module sealing keeps obligations for singleton services that reach a requirement, because the host may register that requirement as scoped. Fallback from the spec: the default stays scoped, and only the child-container rule below is evaluated on its own merits (keep it if it is sound without the flip; decide and document).
2. New rule: `createChildContainer` may replace only scoped and transient services. Replacing a singleton in a child is a compile error whose message names the key and says to mark it scoped or to use an independent container, and a runtime error (choose a failure-kind code; `DI_BAG_CONFLICTING_SERVICE_SELECTION` is reserved by the spec for share-and-replace conflicts; add a new section to `docs/agent/errors.md` for whichever you choose). `createIndependentContainer` may replace anything. A replacement provider may itself be a singleton: it is then anchored to that child and shared with its descendants, as today. Check what happens to `examples/scopes.ts` and the tutorial's scope example, which replace a root `config` in a child: they must change to mark `config` scoped or to use an independent container.
3. `allowsScopedDependencies` still works, now written as `.withLifetime('singleton:one-per-container-tree', { allowsScopedDependencies: true })`.

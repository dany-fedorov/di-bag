# Findings from the controller's throw-site inventory (2026-09-21, at the 0.4.0 source)

Files in the scratchpad: `throw-sites.tsv` (every `DI_BAG_` literal in `src` that is not a type declaration or comment, with its owning call) and `throw-sites-mapped.tsv` (the same rows with a proposed 0.5.0 code, the rule that decided it, and the real message text).

- Completeness check that passed: 123 `DI_BAG_` literals in `src`, all 123 accounted for, 110 rows, all 42 codes present, none unclassified. Rows are NOT throw sites: an error class appears once for `diagnosticMessage` and once for `diagnostic`; a ternary such as `closing ? 'DI_BAG_CLOSING' : 'DI_BAG_CLOSED'` is one row with two codes; six literals are type declarations.
- Result of applying the spec's taxonomy: 29 distinct target codes from today's source. With `DI_BAG_REMOVED_API` and `DI_BAG_WRONG_TOKEN_KIND`, which do not exist yet, that is the spec's "about 31".
- The codes with several meanings split exactly along the spec's targets. `DI_BAG_INVALID_SCOPE`: four malformed-input sites, one unknown key, one missing override, two selection conflicts (share-and-override, share-a-transient). `DI_BAG_INVALID_OVERRIDE`: one malformed input, one unknown key, one missing override. `DI_BAG_INVALID_EXPORT`: three malformed input, two unknown key (`renameExport requires an existing export`, `buildModule accepts existing names...`), one duplicate (`duplicate export`). `DI_BAG_INVALID_METADATA`: one site is a bad describe result (`acquisition metadata must be a synchronous plain object record`), the rest malformed input. `DI_BAG_INVALID_REGISTRATION`: `invalid factory registration` is not-a-provider, the other two malformed input. `DI_BAG_INVALID_STARTUP`: one unknown key, the rest malformed input.
- 52 throw statements map to `DI_BAG_INVALID_ARGUMENT`, plus the internal conditions of the `snapshotOptions` helper. Every message was read, not sampled: each describes the shape of an input. This count is EXACT with the Node extractor `error-code-inventory.mjs` (scratchpad `p12/`, to be committed by the plan as `scripts/error-code-inventory.mjs`): it anchors the message on the literal's position in its own line, so a line can no longer borrow the message of a throw two lines below. An earlier Python version did leak (the helper call at `startup.ts` showed the `startupOrder` message); the two helper lines now carry no message. Seven adjacent pairs share one message and were verified by reading the code to be real twin throws, each with its own condition: `acquisition-mode.ts` (options object, then `isNativePromise`), `composition.ts` (type check, then the catch around the construct probe), `lifetime.ts`, `observers.ts`, `provider.ts` twice, `tokens.ts`.
- Requirement for the plan's table that follows from those pairs: twin throws share a message and almost the same details today, so a caller cannot tell which check failed. Under `DI_BAG_INVALID_ARGUMENT` every row gets its own precise `details.argument` and `details.expected` (for example `argument: 'runtime'`, `expected: 'object'` versus `argument: 'runtime.isNativePromise'`, `expected: 'function'`). Every site is edited in this phase anyway, so this costs nothing extra.
- The shared options validator `snapshotOptions` in `src/startup.ts` receives a code as an argument and throws it from several internal conditions, all malformed input. The edit site for `DI_BAG_INVALID_ARGUMENT` there is the helper, not its two callers; after the change it no longer needs a code parameter.
- Two lessons about trusting the extractor: a first version undercounted (91 rows, 30 codes) because it required the literal right after the opening parenthesis; a second version reported "0 rows need a manual decision" while about forty rows had captured a fragment of CODE as their message (the first quoted span on a long `if (...) throw` line runs from one apostrophe in the condition to the next). Anchor message extraction on the code literal and take the string argument that follows it. Always finish with the completeness check above.
- This table will be stale when phase 11 starts: most messages embed names that phases 3 to 10 rename. Re-run the extraction at phase entry and key every row on its message text and enclosing function, never on a line number.

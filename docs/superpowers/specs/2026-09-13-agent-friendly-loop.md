# Agent-friendly loop

Decisions from 2026-09-13 on making DI Bag easy to use for coding agents that
work on codebases built with it. The organizing rule: an agent must meet the
guidance inside its normal loop, in the file tree, in `node_modules`, in a
compiler message, or in a runtime error, without knowing that a document
exists. Anything that requires the agent to know where to look is out.

This spec supersedes the candidate deliverables and the eval proposal in
`2026-09-13-agent-discoverability-brief.md`. It builds on the shipped and
pending work in `2026-09-13-agentic-scale-hardening.md` (plans 01 to 07) and
does not restate their designs.

## The loop

| Stage | The agent is | Meets guidance through |
| --- | --- | --- |
| L1 Landing | reading the consumer repo | the directory layout |
| L2 Reading the dependency | reading `node_modules/di-bag` | shipped agent docs, `.d.ts` comments |
| L3 Writing code | guessing the API | defaults, names, loud failures |
| L4 Type-checking | reading `tsc` output | messages that name the fix |
| L6 Running | reading a thrown error | messages with code, cause, fix, URL |
| L7 Merging | combining parallel module work | one documented check |
| L8 Keeping it true | not present | drift checks in CI |

Stage L5 (tests) has no measures; see "Not doing".

## Ownership of facts

The set stays consistent only if every fact has one home and every other place
links to it or is generated from it.

| Fact | Home | Everywhere else |
| --- | --- | --- |
| A rule an agent must follow (entry point, lifetimes, thenables, dependency object) | `AGENTS.md` | JSDoc on the API the rule concerns states the same rule in one sentence and links nowhere |
| What a public call does and one example | its JSDoc in `src/` | the API card and the generated reference are generated from it |
| The recommended module layout | `docs/guides/examples-modularity.md` | `AGENTS.md` carries a byte-identical copy, checked in CI |
| A compile-time or runtime message, its cause, and its fix | `docs/agent/errors.md`, one section per code or message | the card's table links to the section; error messages carry the section URL |
| How to do one of the six recipe tasks | `docs/agent/recipes.md` | `AGENTS.md` links to the recipe by anchor |
| The per-module check command and the fast check | `AGENTS.md` | the recipes link to it |
| The merge check | the "review a merge" recipe | `AGENTS.md` links to it |
| The package description | `package.json` | the site configuration reads it from there |

No document restates a fact from another home in different words.

## Decisions

### L1. The layout is the default shape everywhere

- The layout in the modularity guide (one directory per module: `contract.ts`,
  `module.ts`, private services, the module's test, and `src/app.ts` where
  modules meet) is the shape used by every recipe and by every multi-file
  example in the guides. Single-file runnable examples under `examples/` stay
  single-file; inside the file, the order is the same: contract types first,
  private factories, the sealed module, then the host.
- Four additions to the layout, all used by every recipe: `check.ts` and
  `tsconfig.json` in each module directory (L4), `src/app.check.ts` beside
  `src/app.ts` (L7), and one `installModule` call per line in `src/app.ts` (L7).
- No scaffold command and no separate example application.
- Acceptance: grep for `buildModule(` in `docs/guides` and `docs/agent` finds
  no example whose file order differs from the layout.

### L2. What ships in the package

The package `files` become `['dist', 'AGENTS.md', 'docs/agent']`.
`scripts/verify-release-artifacts.ts` (lines 113 and 115) and
`tests/release-artifacts.test.ts` change accordingly. The zero-dependency
contract does not change.

- **`AGENTS.md`** at the repository root, at most 150 lines, self-contained:
  what the library is in three lines; the rules (which import, default
  lifetime and the root-capture rule, thenables, the dependency object is a
  Proxy and must be destructured or read directly, how to read a rejection and
  where `verifyGraph()` goes); the layout block; the per-module check command
  and the fast check (L4); a link to the merge recipe (L7); links by anchor
  into `docs/agent/`. It does not describe the API.
- **`docs/agent/api-card.md`**, at most 400 lines, generated by
  `tools/docs/generate.mjs` from the JSDoc of the public runtime surface
  (`DiBag` facade members, `Builder`, `Bag`, the error classes): one line per
  call with its one-sentence summary, followed by its `@example` block. A
  "one way per task" table maps each task an agent gets (register a service,
  attach cleanup, choose a lifetime, seal a module, install a module, replace
  for a test, open a scope, resolve, close) to exactly one call. If the table
  cannot name one call for a task, that is a finding against the API and goes
  into the changelog draft, not into the card.
- **`docs/agent/recipes.md`**: six recipes, each under 60 lines, each in the
  layout. The five audit tasks from the brief: add a request-scoped service
  with cleanup; write a fixture test with `fork`; split a feature into a module
  with private services; debug a missing-dependency rejection; add and consume
  an async client. And the merge check from L7: review a merge.
- **`docs/agent/errors.md`**: one section per `DI_BAG_*` code (37 today, from
  `grep -rho "'DI_BAG_[A-Z_]*'" src | sort -u`) and one per compile-time message family
  (missing service, unsatisfied consumer, root capture, unknown key, structural
  thenable, wrong shape, wrong override). Each section: when it appears, the cause, the fix
  with a snippet, and which recipe applies. Its anchors are the URLs that
  messages carry (L4, L6).
- **JSDoc**: every exported runtime declaration has a one-sentence summary, an
  `@example` that compiles, the `@throws` codes it can raise, and, where a rule
  from `AGENTS.md` applies, that rule in one sentence. Exported types keep a
  summary and gain `@see` to the guide anchor that explains them. The generator
  already refuses a missing comment; it additionally refuses a missing
  `@example` on the runtime surface listed above.
- **Erased module declarations** (plan 07) are adopted in full: every
  `buildModule` seals to a `Module` whose exports, requirements, and public
  providers print as resolved object types, and whose retained lifetime state
  is a set of compact reach records instead of the module's private
  registrations. Decided 2026-09-13 on the per-module measurement this rule
  asked for (an 8-module consumer fixture reading the built `.d.ts`, medians
  of 5): the type-check time of one module directory with its `check.ts` did
  not change (0.24 to 0.33 s on TypeScript 6.0.3, 17 to 37 ms native,
  identical within noise on both branches) while instantiations rose 2 to 7%
  per module on 6.0.3 and 11 to 21% native. An instantiation increase that is
  linear in module size and invisible in wall time is a cost, not a
  regression: the ceilings guard against superlinear blow-ups, so they are
  raised to uniform headroom rather than read as a verdict. Two further
  results decided it. A private factory edit that changes an inferred return
  type leaves the emitted declaration unchanged under erasure, so `check.ts`
  and `src/app.check.ts` are not rechecked (25k instantiations, 0.01 s) where
  today they are (244k, 0.12 s; 426k, 0.25 s native); that is the edit agents
  make repeatedly. And the declaration shrinks five to ten times (7.6 to
  18.2 KB down to 0.8 to 2.3 KB), so hovering a sealed module or reading its
  `.d.ts` shows `Module<{ exports }, Readonly<{ requirements }>, ...>` with no
  private type and no private registration shape. The opt-in projection is
  rejected: it puts erasure behind a call the agent must know exists, against
  the organizing rule, and keeps two module type shapes to test. Conditions
  carried into the work: requirement records print each named need once
  (symbol-keyed token needs stay `Record` references because declaration
  emit cannot expand a unique-symbol property); private registration keys may
  remain only as quoted string literals inside constraint records
  (`consumer`, `root`, `export`, `reach.key`), where they give the host's
  diagnostics their provenance, and a test pins that boundary; the four
  ceilings in `tests/incremental-scale.test.ts` become 810,000 / 1,060,000 /
  870,000 / 1,275,000, about 3% above the measured values, the headroom the
  L4 message-URL work also needs; and the three `1000 providers from reusable
  named modules` cases are timed back to back against `main` on one machine
  before merge, with the branch at most 1.25 times `main`, because the
  earlier 83 s against 45.5 s figure was taken under different load.
- **Package metadata**: the description is the one in the working tree on
  2026-09-13 ("DI container for agent-built codebases: the compiler checks the
  wiring, modules stay private, resources get cleaned up."); the site
  configuration reads it from `package.json` instead of holding its own copy;
  keywords gain `agents`, `coding-agents`, `modules`.
- Acceptance: `npm pack --dry-run` lists exactly `dist/`, `AGENTS.md`,
  `docs/agent/`, `README.md`, `LICENSE`, `package.json`; the card is at most
  400 lines and `AGENTS.md` at most 150, enforced by the docs check.

### L3. The API an unread agent would guess

- **Entry point.** Today `di-bag` is portable and throws
  `DI_BAG_CLASSIFIER_REQUIRED` at `build()`, and agents import it because it
  is the package name. Decision: the bare entry configures itself on hosts
  that expose `process.getBuiltinModule` (Node, Bun; Deno to be verified in
  the platform lane) by loading `node:util/types` at first `build()` through
  that call, without a static `node:` import, so the release invariant
  `rootLoadsNode: false` and the browser-bundle check (no `node:` input in the
  esbuild metafile) both still hold. Elsewhere it stays portable and
  `DI_BAG_CLASSIFIER_REQUIRED` still fires at `build()`, with this message
  text, specified here and nowhere else: `this host has no
  process.getBuiltinModule; configure DiBag.withConfiguration({ runtime: {
  isNativePromise } }) or give each automatic registration an explicit
  acquisitionMode`. The message cannot name an import line, because on the
  host where it fires detection has failed. `di-bag/node` stays as the
  explicit form and becomes the second choice in the docs. The fallback if the platform lane
  rejects the mechanism: keep today's behavior and make `import { DiBag } from
  'di-bag/node'` the first rule in `AGENTS.md` and the first line of every
  example.
- **Lifetime default** stays `scoped`: one cached instance per bag or child
  scope. The rule in `AGENTS.md` and in the JSDoc of `withLifetime`: mark a
  shared client `root` only when nothing it depends on is scoped; the root
  capture rejection already names both keys.
- **One way per task** is enforced through the card's table (L2), not through
  API removals in this change set.
- **Names** stay: `register`, `build`, `buildModule`, `installModule`,
  `resolve`, `fork`, `createScope`, `close`. No rename map (no users yet).
- **Loud failures**: proxy guards (plan 02) and the thenable check (plan 04)
  are shipped in 0.2.0. Nothing to add.
- Acceptance: the quickstart compiles and runs with `import { DiBag } from
  'di-bag'` on Node and Bun; the browser-worker platform lane stays green.

### L4. Compiler messages that end the search

- **Messages carry the fix location.** Every named compile-time message
  (missing service, unsatisfied consumer, root capture, unknown key, thenable)
  ends with the `docs/agent/errors.md` site URL for its family, for example
  `required service registrations are missing: clock; see
  https://dany-fedorov.github.io/di-bag/agent/errors.html#missing-service`. The
  three wrong-shape sites that stay generic for compiler-cost reasons (plan 03
  deviation) carry the URL of the section that says to call `verifyGraph()`.
  Template-literal cost is measured against the ceilings in
  `tests/incremental-scale.test.ts` before merge.
- **Per-module check file.** Each module directory gets `check.ts` containing
  one statement: a builder that installs the module, registers a typed fixture
  for each requirement, and calls `verifyGraph() satisfies void`. It has no
  runtime effect and is excluded from the build. This is the isolated
  type-check of a module and needs no new API.
- **Per-module type-check command.** `AGENTS.md` carries the command, and the
  recipes link to it: `tsc --noEmit -p src/features/<name>/tsconfig.json`,
  where that tsconfig extends the root one and includes only the directory.
  Its wall time is the number plan 07's decision rule uses (L2).
- **Fast check.** `AGENTS.md` also defines the consumer-side `check:fast`
  script as the per-module type-check plus that module's test file, to run
  after every edit; the full suite runs before merge.
- Acceptance: the negative fixtures' expected messages include the URLs; the
  site check resolves every URL cited in a message; a module with a missing
  requirement fails `check.ts` with a message naming the key.

### L6. Runtime errors that are the documentation entry point

- **Message format** for every library-created error becomes
  `<code>: <message>; see <site URL>#<fragment>`, where the fragment is the
  code lower-cased with underscores replaced by hyphens, which is what the
  site's heading slugifier produces. For example
  `DI_BAG_CYCLE: cycle: a -> b -> a; see
  https://dany-fedorov.github.io/di-bag/agent/errors.html#di-bag-cycle`. `code` and
  `details` stay as structured fields and remain the supported way to branch;
  the message is for people and agents reading a stack trace. The tests that
  assert message text (about ten assertions today) are updated. This is a
  breaking change for anyone matching message text and is recorded as such.
- **Module labels.** `buildModule(keys, { label })` gains an optional label.
  Private bindings of an installation are labeled `<label>/<key>` in error
  messages, cycle paths, `inspectGraph()`, and observer events; without a
  label they keep today's bare key. The API additions in L6 are this option
  and the close deadline below; nothing else changes shape.
- **Cycle messages** already print the path. Nothing to add.
- **Classifier error** carries the message text specified in L3.
- **Close deadline.** `close({ timeoutMs?, signal? })` mirrors startup. When
  the wait stops it rejects with `DiBagCloseCancelledError`, whose `code` is
  `DI_BAG_CLOSE_TIMEOUT` for the deadline and `DI_BAG_CLOSE_ABORTED` for the
  signal; `details.pending` lists the labels of disposers that have started and
  not completed, `details.acquiring` the acquisitions close was still draining,
  and `cleanupPromise` settles when cleanup eventually finishes, as
  `DiBagStartupCancelledError` does. Malformed options reject with
  `DI_BAG_INVALID_CLOSE`. Without options, `close()` waits as it does now, so
  the README tradeoff "cleanup waits for your work" is reworded to "by default".
- Acceptance: every code in `src` has a section in `docs/agent/errors.md`
  (checked in CI); every message URL resolves; `close({ timeoutMs: 1 })` on a
  bag with a never-settling disposer rejects naming that disposer.

### L7. One merge check

- `verifyGraph() satisfies void` on the application builder in
  `src/app.check.ts`, plus the full test suite, is the merge check. Its home
  is the "review a merge" recipe; `AGENTS.md` links to it. It catches
  a missing requirement and an incompatible contract at the type level. It
  does not catch dependency cycles, which the runtime reports at first resolve.
- Therefore `di-bag-graph` is published as its own npm package (it depends on
  TypeScript, which DI Bag must not), with `di-bag-graph --check` as an
  optional CI step that fails on cycles and unresolved names before any
  factory runs. The harness guide's graph section moves to
  `docs/agent/recipes.md` as "review a merge", and keeps the framing from the
  README: a merge-review and CI artifact, not a code map.
- `src/app.ts` keeps one `installModule` per line so parallel branches merge
  without conflicts. Stated in the layout block, nowhere else.
- Acceptance: the recipe runs against the modularity guide's three programs
  combined into one app; introducing a two-module cycle fails `--check`.

### L8. Drift control

- **Snippet check.** `npm run docs:check` gains a step that extracts every
  `ts` block from `AGENTS.md`, `docs/agent/*.md`, and every `@example` in
  `src/`, resolves `di-bag` and `di-bag/node` to `dist/`, and type-checks them
  in one shared program (the `tests/compiler.ts` approach). Three leading
  markers the extractor honors: `// continues: <anchor>` prepends the named
  earlier block; `// expect-error: <fragment>` requires the block to fail with
  a diagnostic containing the fragment, which is how the errors page and the
  missing-dependency recipe show rejected code; and a file path such as
  `// src/features/x/module.ts` makes the block that file, so blocks on one
  page import each other.
- **Generated card.** The API card is never edited by hand; `docs:check`
  regenerates it and fails on drift, as it does for `docs/reference/`. The
  generator refuses a runtime call without `@example`; the task table's source
  is `tools/docs/api-card-tasks.json`.
- **Layout block identity.** `docs:check` asserts the layout block in
  `AGENTS.md` is byte-identical to the one in the modularity guide.
- **Code coverage of errors.** `docs:check` asserts the set of `DI_BAG_*`
  codes in `src` equals the set of code-anchored sections in
  `docs/agent/errors.md` (the message-family sections are additional), and
  that every URL in a message resolves in the built site.
- **Size budgets.** `docs:check` fails when `AGENTS.md` exceeds 150 lines, a
  recipe section in `docs/agent/recipes.md` reaches 60 lines, or the card
  exceeds 400.
- **Eval.** `scripts/agent-eval/` runs the parallel-modules eval from the
  brief: several agents, each seeing only the installed package and one module
  directory with its contract, implement their modules against a fixed
  application skeleton; the score is whether the merge passes `check.ts`
  files and tests on the first attempt, and iterations per agent, with a
  single-agent run as baseline. It is run by hand before a release and its
  results are recorded under `docs/benchmarks/`; it is not a CI gate, because
  it costs money and is not deterministic.
- **Changelog** per release as today. No rename map.

## Not doing, and why

- Stage L5 measures (fixture conventions beyond the recipe, in-memory adapter
  patterns, `inspectGraph()` assertions): the fork recipe already shows the
  one way to isolate a module; the rest adds convention without discovery.
- A rename map: there are no users to have learned the old names.
- `llms.txt`, a paste-in block for consumer instruction files, tool-specific
  skill or rules files, an MCP or CLI docs search, a scaffold command, a
  shipped glossary, a page of negative fixtures, a "for coding agents" block in
  the README: each requires the agent to know to look, or duplicates
  `AGENTS.md`.
- A separate canonical example application: the layout is shown by the
  recipes and the modularity guide; another copy would drift.

## Documents that must change to stay consistent

- README: tradeoffs ("cleanup waits for your work" becomes "by default";
  "dependency cycles are detected at runtime" gains "or by `di-bag-graph`");
  runtime support table (bare `di-bag` self-configures on Node and Bun); the
  quickstart and every example import from `di-bag`, with `di-bag/node`
  mentioned once as the explicit form; Explore further gains a row for
  `docs/agent/` and its "Static dependency graph" row points at the merge
  recipe.
- Tutorial: the introduction and every example import from `di-bag`; the
  portable-mode section; the section on reading rejections (URLs in
  messages); `close()` options.
- `docs/guides/api-reference.md`: import guidance (`di-bag` first); errors
  section links to `docs/agent/errors.md` and shows the message format.
- `docs/guides/examples-modularity.md`: the layout block gains `check.ts`,
  the per-module `tsconfig.json`, `src/app.check.ts`, and the one-install-per-
  line rule, since it is the layout's home.
- `docs/guides/agent-harnesses-and-graphs.md`: graph section replaced by a
  link to the merge recipe.
- `docs/guides/documentation.md`: the snippet check, the generated card, the
  size budgets, the errors page ownership.
- `tools/docs/site.mjs` and `vitepress.config.mjs`: the site build includes
  `docs/agent/` at `/agent/`, so the URLs in messages resolve; the sidebar
  gains an "Agent docs" group; the site description is read from
  `package.json`.
- `docs/superpowers/specs/2026-09-13-agent-discoverability-brief.md`: marked
  as superseded by this spec for deliverables and the eval.
- Plan 07 status: decision rule replaced by the one in L2.
- `CHANGELOG.md` at the next release: breaking (message format, bare entry
  self-configures), added (`close` options, `buildModule` label,
  `DI_BAG_CLOSE_TIMEOUT`, shipped agent docs, published `di-bag-graph`).

## Sequencing

1. L8 snippet check and size budgets first, on the existing docs, so every
   later document is checked from its first commit.
2. L2 `AGENTS.md`, recipes, errors page, package `files`, release-contract
   updates. Text only; ships value immediately.
3. L2 JSDoc examples and the generated card, since the card depends on them.
4. L6 message format, module labels, classifier wording, close deadline. One
   `src/` change set with the test updates.
5. L4 message URLs, `check.ts` convention, per-module tsconfig recipe.
6. L3 entry-point self-configuration, gated on the platform lane.
7. L7 publish `di-bag-graph`, merge recipe.
8. L2 plan 07 decision, after the per-module measurement from step 5 exists.
9. L8 eval, last; it measures the result of everything above.

## Global constraints

Those of `2026-09-13-agentic-scale-hardening.md` apply unchanged: TypeScript
6.0.3 minimum with native 7.0.2 passing, zero dependencies, strict tsconfig,
`npm run check` before every commit, `docs:generate` then `docs:check` after
comment or export changes, no `## Unreleased` section, no compatibility
aliases, terse factual documentation.

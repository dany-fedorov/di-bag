# di-bag v0.1 design

## Agreed direction

Deliver the entire standalone v0.1 milestone. Dependencies remain inferred
from factory parameter types. Async edges are explicit promises: a factory
requiring an async database declares `{ database: Promise<Database> }` and
awaits it. Synchronous factories and resolution stay synchronous.

The optional lifecycle helper is `DiBag.withDisposal(create, dispose)`.
Ordinary factories remain `(dependencies) => value`. The helper returns a
branded registration containing the factory and its cleanup callback, without
running either. Consumers receive the factory's value, never the registration.
The disposer receives `Awaited<ReturnType<typeof create>>` and returns
`void | Promise<void>`.

## API and compile-time guarantees

`DiBag.begin().add(registrations).end()` builds a lazy bag. `resolve(token)`
returns the exact factory return type, including promises. Every declared
dependency key must be provided, including optional properties; dependency
parameters must be single finite objects with string keys (union and callable
parameter types are rejected). Dependency shape checks
run across the entire merged graph at every `.add()`, in either registration
order, including replacements. Builders are immutable snapshots.

`.end()` becomes a method with a conditional receiver constraint naming
missing tokens. A return-only error type would allow an unused invalid
`.end()` call to compile, so the method must reject the call itself.

`fork(overrides)` accepts existing tokens only. Each override must preserve
the original token's provided type, and the merged graph is checked for
dependency shapes and totality. A fork has independent memoization and
resource ownership; it can replace a disposable registration with an ordinary
factory when borrowing an externally owned value. The fork's type reflects
the merged registrations. Parent and fork close independently.

## Resolution and lifetime

Resolution uses a lazy property proxy and memoization. Sync failures and async
rejections are retryable; concurrent async resolutions share the same promise.
The runtime records dependency edges when a factory reads a property, including
reads after `await`. A cycle throws or rejects with its token path. Registry
lookups use own string keys, preventing accidental prototype resolution.
The proxy supports named reads, not enumeration or spreading dependencies.

Only `withDisposal` registrations are owned. Successful owned creations are
recorded once per bag; failed and never-resolved factories have no cleanup.
Unwrapped values with a `dispose` or `close` method are not automatically owned.
Registering the same external instance as owned in multiple bags is the
caller's ownership error; use ordinary factories for borrowed instances.

`close(): Promise<void>` immediately stops public resolution and forking, drains
in-flight factories (including dependencies they discover while completing),
then awaits cleanup callbacks sequentially. Dependents close before their
dependencies, with reverse successful acquisition order for unrelated resources.
Dependency ordering takes priority over completion order for async graphs.
All cleanups run even if one throws or rejects; close rejects with the first
cleanup error, including non-Error thrown values. Repeated close calls return
the same promise and never dispose twice. The bag is closed even on failure.
Acquisition failures remain on their resolution promises and do not count as
cleanup failures. Applications must stop using services before closing;
already-returned values cannot be revoked. A factory that never settles makes
close wait indefinitely; cancellation and timeouts are outside v0.1.

## Package and evidence

- Runtime has zero third-party dependencies and no platform-specific APIs.
- TypeScript 5.9.3 is the development compiler; strict checks are enabled.
- Bun runs runtime tests; individual TypeScript fixtures prove each rejection.
- Compile-positive tests cover sync/async factories, forks, and typed cleanup.
- Negative tests include missing keys, both mismatch orders, replacements,
  invalid fork shapes/keys/requirements, async-to-sync misuse, bad disposers,
  and unsupported dependency shapes.
- Tests cover diamonds, forks, cycle paths across awaits, retry behavior,
  pending shutdown, cleanup order, cleanup failures, and double close.
- Package version is 0.1.0, with JavaScript and declarations emitted to `dist`.
  Verify both Node `require` and ESM named import of the built CommonJS entry;
  browser consumers use a bundler. Bun is development tooling only.
- Archive historical experiments under `docs/history/` instead of destroying
  them. Only the current implementation remains in `src/`.
- `npm test`, `npm run typecheck`, `npm run build`, and `npm pack --dry-run`
  provide reproducible release checks. The tarball includes only distribution,
  README, package metadata, and license. Publication is a separate action.

## Future investigation

Investigate how Effect derives dependency requirements through typed effects
and layers without duplicating dependency declarations. This question is
explicitly deferred; v0.1 uses the agreed explicit-promise model. Do not claim
Effect's mechanism has been researched yet.

## Approved WBS validation increment

The follow-up design interview confirmed a local WBS-shaped example before
publication. Sharing is configured explicitly in each `fork` through ordinary
factories returning root instances; no factory-level lifetime API is added.
An explicitly shared service retains its original dependency instances.

Application startup owns the source it opens and is responsible for initiating
bag shutdown. Bags dispose only their `withDisposal` registrations. The example
closes borrowing batch bags before the root bag and finally the application-owned
source, continuing cleanup if a preceding close fails. A factory must clean up
partially acquired resources if it fails before returning a value.

Use small in-memory stores, a clock, a replay buffer, per-batch announcement
collectors, and a work-item service to demonstrate the boundaries. The example
models planned WBS composition; it does not import WBS or validate its SQL
transactions. Verify identity sharing, fresh scoped services, isolated collectors,
unchanged dependencies of explicitly shared services, and successful/failing
shutdown paths. Keep the public di-bag API and publication contents unchanged.

## Approved inline factory inference correction

Support inline factories returning objects with methods in both `.add()` and
`.fork()`, including mixed disposable registrations. Preserve their inferred
return types and all existing registration-map, dependency, totality, and override
checks. Do not add an API or change runtime/disposal behavior.

Infer each registration map's actual keys before validation, while retaining the
original requirement that inputs are registration maps. Cover the correction
with exact-type positive fixtures, negative validation fixtures, and emitted
package declaration checks. Remove the WBS example's separate-factory workaround
once the inline form passes these checks.

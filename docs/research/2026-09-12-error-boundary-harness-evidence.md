# What Application Exception and CORJ actually contribute to an agent harness

Audit date: 2026-09-12. This report separates implemented mechanisms from benefits that require application code and from claims that still need experiments. “Harness” means the host code that executes operations, records outcomes, exposes selected observations, and decides what happens next. Neither package is itself that host.

Primary evidence is checked-out source and tests. Application Exception is package version `0.2.1`, initially clean HEAD `417308aaa144ddcc12ade8118e52b22c0e878918`. CORJ is package version `9.0.0`, HEAD `f74c3fa21ad3f8fd24a684b06b83f5ea7e0b4ab5`; its README, docs/index.html, package.json and new example-12-agent-harness.ts contained existing working-tree changes. Runtime findings below concern the checked-out runtime, which was unchanged from HEAD. Discussion of CORJ's new wording/example concerns that unpublished working-tree state. Subsequent documentation follow-through added rationale pages, qualified README claims, and regenerated CORJ's documentation; runtime code and existing example/package changes were preserved.

## Chapter 1 — Application Exception: local failure kinds and a deliberate reporting boundary

### The concrete problem and the actual package

A tool fails, but several consumers need different answers. Application code needs to distinguish a known unavailable service from an unexpected defect. Operators need the underlying provider failure. The model needs a small, intentionally selected explanation and a reference, not an arbitrary backend object. Correlating those views without interpreting prose is a legitimate harness problem. It is also an ordinary service-boundary problem; nothing about it inherently requires an LLM.

The current package addresses all three representations. Its public API exports `defineException`, `isTypedException`, `toDiagnosticReport`, `toPublicReport`, and `decodeDiagnosticReport`. Describing it merely as “typed codes and metadata on Error” misses most of the current implementation. Equally, calling it an agent recovery system overstates it: it exports no executor, scheduler, persistence store, retry engine, authorization policy, or model adapter. The repository's domain model explicitly separates error kind, occurrence, diagnostic report, public report, observation context, and failure translation. [API exports][a-api]; [domain model][a-context].

`defineException` creates an actual `Error` subclass. The error carries literal `_tag`, an occurrence `id`, ISO creation `timestamp`, copied details, message, and optional native-style `cause`. A string message permits an omitted constructor input; a renderer with an annotated details parameter produces a constructor requiring those details in TypeScript. The tag is a stable application-chosen kind; the public report's `code` is a separately selected protocol value. No built-in mapping connects the two. That separation permits different public presentations of the same internal kind for different audiences. [Construction][a-typed]; [public projection][a-reporting].

### What is demonstrated, including limits on “typed” and “stable”

A host can narrow an unknown value with `instanceof ToolUnavailable`, or use `_tag` exhaustively after it already has a known union of exception types. The repository checks these TypeScript contracts and has an Effect example using `Effect.fail` and `catchTag`. The narrow conclusion is compatibility with those explicitly demonstrated operations, not universal framework integration or automatic classification of unknown errors. A catch variable remains `unknown` until the host supplies a trustworthy narrowing step. [Type assertions][a-types]; [Effect test][a-effect].

Runtime constructor checks validate tag/prefix length, non-array record details, enumerable data-only own properties, limited prototype inspection, and mutually exclusive cause forms. They do **not** validate each field against the inferred TypeScript details type. An executable probe constructed a kind whose renderer requires `{ tool: string }` with `details: {}` through an unchecked call; construction succeeded with message `Unavailable: undefined`. External JSON therefore needs its own schema validation before becoming trusted application input. An interface is not a runtime decoder. [Construction checks][a-typed]; probe results below.

Details are shallow-copied and shallow-frozen. The top-level snapshot prevents a caller from later replacing an input field and silently changing the copied record. Nested objects remain shared: mutating the original nested object changed the error's nested detail in the probe. Moreover, TypeScript `readonly` on `_tag`, `id`, and other class fields is not an immutable JavaScript descriptor; `_tag` was runtime-writable. Occurrence identity is an application convention and generated value, not an authenticated, tamper-proof identity. [Construction tests][a-typed-tests].

`isTypedException` consults a module-local `WeakSet`. It rejects a copied JSON record, a forgeable global-symbol brand, and instances created by another loaded copy of the library. This is a useful local-instance guard, not a validator for remote detail schemas. Diagnostic reporting intentionally has a weaker, descriptor-based foreign-copy view so it can retain recognizable metadata without granting the stronger local guarantee. A valid diagnostic report likewise does not become an executable typed exception after decoding. [Internal trust distinctions][a-internals]; [foreign-copy tests][a-bounds].

A single cause is retained by object identity as a non-enumerable property. Several causes become an ordered native `AggregateError`; a single-element `causes` array collapses to that element, and an empty array installs no cause. These are concrete interoperability decisions that preserve causal information for an adapter to inspect. They do not prove that the supplied cause is causally correct. Wrapping an error also creates a new occurrence; repeated observation should instead retain the occurrence and add report context. [Cause installation][a-occurrence]; [observation tests][a-observations].

### Diagnostics, disclosure, and host ownership

`toDiagnosticReport` accepts an unknown caught value and produces JSON-compatible data with report version, reference, name, message, timestamp, and, where recognized, kind/details/cause. Non-Error thrown values become an explicit `thrown` representation. Native causes retain selected diagnostic fields including bounded provider `code`/`status`; arbitrary extra Error properties are not all copied. Normalization marks cycles, unsupported collections, unreadable accessors, truncated content, and values JSON cannot faithfully represent. Dates receive special handling. Stacks are omitted unless explicitly requested. [Reporter][a-reporting]; [normalizer][a-normalizer].

Defaults bound depth to 8, normalized values to 1,000, entries per container to 50, strings to 4,096 UTF-16 code units, and final compact JSON to 65,536 UTF-8 bytes. If the final envelope exceeds its allowed byte budget, the producer returns a compact envelope with diagnostics omitted. This is a measured output contract, not a promise that every diagnostic detail survives. Tests exercise escaping, multibyte text, edge-limit combinations, repeated graphs and decoder compatibility. [Limits and traversal][a-normalizer]; [bounds tests][a-bounds].

The normalizer uses property descriptors rather than invoking ordinary getters, custom `toJSON`, or custom object string conversion. It redacts selected key names before reading their descriptors; defaults include `password`, `token`, `authorization`, `secret`, and several others, with caller additions. These are meaningful defensive choices for reporting values that may behave unexpectedly. They are not process isolation: `Reflect.ownKeys` still enumerates the input's width, and a proxy trap can execute arbitrary code before a JavaScript `try` block receives a thrown exception. A synchronous nonterminating trap cannot be interrupted by the report's byte limit. [Descriptor access and enumeration][a-normalizer]; [getter/proxy tests][a-report-tests].

Nor is key redaction general secret removal. A secret inside a message, a URL, a stack when enabled, or an innocently named field can remain. The strongest disclosure boundary is architectural: `toPublicReport(reference, presentation)` receives no error object at all. Its default has only version, reference, `INTERNAL_ERROR`, and `Something went wrong`. The host must explicitly select a public code, message and optional details. Passing sensitive text explicitly still reveals it. Diagnostic output is therefore appropriate for a trusted operational destination under application policy; being bounded and JSON-compatible does not make it model-safe. [Public implementation][a-reporting]; [public tests][a-report-tests].

The agent recovery example supplies the missing host layer: AJV validates the public envelope, the host allowlists retryable codes, checks an integer remaining-attempt budget, selects an operation from its own policy, and returns a retry/escalate record. Tests establish that changing message prose does not change the decision. This demonstrates deterministic **example policy**, not retries performed by the library. Authorization, idempotency, backoff, rate limits, execution, persistence and operation-specific safety remain host responsibilities. Even schema-valid `TOOL_UNAVAILABLE` does not establish that repeating a payment is safe. [Recovery implementation][a-recovery]; [recovery tests][a-recovery-tests].

### Claim ledger and native alternatives

| Claim | Classification | Exact support or missing condition |
| --- | --- | --- |
| Stable local error kinds, typed constructor details and cause retention | Demonstrated mechanism | Source and runtime/type tests; tags/details still need host semantics and runtime trust boundaries. |
| Separate bounded diagnostics and explicit public presentation | Demonstrated mechanism | Distinct producer APIs, shared reference, normalization and final byte checks. |
| More predictable agent recovery | Conditional benefit | Host must validate external envelopes and implement code-based, operation-aware policy. Example tests cover one such policy. |
| Smaller or safer model context | Conditional benefit | Selected public reports can exclude diagnostic material; actual disclosure and final prompt/token size remain host decisions. |
| Faster debugging, better LLM task completion or lower token cost | Unmeasured hypothesis | No comparative human or model study was run; unit tests cannot establish these outcomes. |
| Automatic retry safety, prompt-injection prevention, distributed replay or immutable event history | Unsupported | No corresponding runtime mechanism; occurrence reports are mutable data and omit execution state. |

The native baseline is already capable: `new Error(message, { cause })`, `AggregateError`, a small custom subclass or tagged record, and explicit `{ code, message, reference }` projection can implement the essential boundary. The probe confirmed that `JSON.stringify(new Error('outer', { cause }))` returns `{}` under the audited Node runtime, because relevant properties are non-enumerable. A deliberate record fixes that basic serialization problem with little code; comparing only against naïve stringification would flatter the library unfairly.

The package's incremental value is the reusable combination of typed construction, occurrence correlation, defensive bounded normalization, explicit projection, and report decoding. That can be worthwhile when many tool/service boundaries otherwise reimplement those contracts inconsistently. It is less worthwhile for a small application with one known failure record and an existing tested logger/projection, or a result-based codebase that already has its own error union and diagnostics. Native causes already solve causal chaining; the library adds consistent representation and reporting conventions around them. Its own diagnostic producer also reduces the need to add CORJ solely to serialize these errors. [API surface][a-api]; [reporting tests][a-report-tests].

### Honest wording and a falsifiable adoption test

The current headline, “Typed failures for agent tools. Bounded diagnostics for operators. Explicit reports for recovery decisions,” has support if the last phrase means reports *consumed by host decisions*. A precise expansion is: “Define native TypeScript error kinds, produce bounded diagnostic JSON, and explicitly select a public failure report that host code can validate and handle.” “Runtime-validated typed failures,” “safe recovery,” or “secure context” would need narrower qualification. The README's existing warning that the package does not execute tools should remain prominent. [Current README][a-readme].

Evaluate adoption against two serious baselines: native Error/cause with a hand-written tagged subclass and public projection; and the application's existing logging/validation stack. Feed all three identical known failures, unexpected throws, aggregate causes, credential-bearing fields, cycles, foreign instances, malformed envelopes and oversized values. Hold the host retry policy constant. Score preserved required facts, unintended disclosures, final UTF-8 size, invalid-envelope rejection, policy outcomes, inspection work and maintenance code. Test model usefulness separately on a fixed failure corpus with blinded success criteria and actual tokenizer measurements. If the same policy and essential observations fit equally well using the simpler baseline, the agent-specific adoption claim fails even though the library's mechanics remain correct.

## Chapter 2 — CORJ: a diagnostic representation of caught values, not an execution graph

### The concrete problem and actual conversion

An agent node can throw a native Error, an SDK-specific error, an AggregateError, a string, null, a cyclic object, or an object whose property reads throw. A log sink or test harness benefits from one recognizable diagnostic envelope instead of special-casing every thrown shape. CORJ implements that representation problem through `makeCorj`, `makeCorjArray`, and a reusable `CorjMaker`. This is useful at a harness boundary, but equally useful in a backend or CLI without any model. [CORJ types and implementation][c-api].

The reporter captures `instanceof_error`, `typeof`, constructor name, message, stack, string representation and JSON representation where available. It uses separate views because ordinary JSON serialization of an Error misses its message and stack; custom enumerable fields may carry additional diagnostics. `as_json` is produced using a bundled serializer and excludes the configured immediate child-source properties to avoid duplicating those relationships there. It can use custom `toCorjAsString` and `toCorjAsJson` methods. Those hooks are application-supplied behavior, not universal SDK adapters. [Field production][c-api]; [serializer][c-serializer].

Default child sources are `cause` and `errors`. Discovery walks breadth-first, assigns IDs and JSONPaths, and reports each encountered object once. Repeated objects point at the first ID. `makeCorjArray` includes the root row and its `child_ids`, making direct parent/child links explicit. In the probe, an AggregateError containing the same Error twice produced two rows total and root links `['0', '0']`. That is evidence of identity-aware diagnostic graph representation. [Discovery and array construction][c-api]; [graph tests][c-tests].

These IDs are not run IDs, tool-call IDs, or durable occurrence IDs. Defaults are `root` and local discovery indices; `path` denotes a property route such as `$.cause.errors[0]`; `level` denotes nesting. Custom `makeReportId` supplies strings but the host must give them any meaningful external identity. A cause graph also does not record attempted operations, prompts, tool outputs, scheduling, timestamps, side effects, or state transitions. Describing CORJ as supporting reporting *at agent graph nodes* is accurate. Describing its output as the agent execution graph or a replay trace is not. [Node contracts][c-api].

### What bounded and compact actually mean

Default `maxReportSize` is 100,000 UTF-8 bytes of the entire compact JSON report, including reported children. The configurable minimum is 256; null disables the size limit; `utf16-code-units` changes the unit to serialized string length. `maxDepth` defaults to 5 and `maxChildren` to 100 for discovered child reports. These settings offer a concrete knob for diagnostic payload volume. They do not measure relevance to a model task. [Options][c-api]; [size implementation][c-size].

The limiter trims content, can discard later child nodes, removes links to discarded nodes, records truncation/omission, and can fall back to a minimal root report. Metadata can be removed to fit. The tests check valid serialized JSON, schema conformance, retained-link consistency, exact fits, Unicode, escaping, and custom IDs over multiple budgets and formats. These are strong finite-fixture checks of representation invariants. They do not guarantee retention of the one nested message needed to diagnose a particular task; breadth-first discovery and field trimming are not semantic prioritization. [Whole-report invariant tests][c-invariants]; [limiter][c-size].

Expected-value omission is a second, distinct mechanism. Under the default compact convention, missing fields can mean `instanceof_error: true`, `typeof: 'object'`, `as_json: {}`, or default formatting/child-source values. Message, constructor name, and string form can be reconstructed from a matching first stack line. `restoreExpectedValues` expands those conventions and relabels version/schema metadata to the full form; it does not recover discarded content or missing metadata. A consumer that ignores these conventions can confuse omitted defaults with absent facts. [Omission/restoration implementation][c-expected]; [tests][c-expected-tests].

The byte guarantee applies at the producer's output boundary. The probe produced an exactly 256-byte compact report; restoring expected values enlarged it to 399 bytes, and surrounding the original with a 300-character run ID enlarged the record to 577 bytes. Pretty printing, report arrays accumulated over a run, tool wrappers, and prompt instructions likewise consume additional space. A report budget is neither a whole-request budget nor a token budget. The host must measure the actual final representation with the target tokenizer when token fit matters. A numeric byte limit alone does not show lower token cost or better context selection.

### Robust reporting is not isolation or disclosure control

CORJ directly reads properties using `prop in host` and `host[prop]`. It calls `String(obj)`, may call user-defined formatters and `toJSON`, reads stacks, and enumerates object keys. It catches many resulting exceptions and emits partial reports rather than letting every getter failure abort reporting. The probe's throwing `message` getter was invoked twice: once for the message field and once during JSON production. App Exception's descriptor-based normalizer invoked it zero additional times. These are materially different inspection policies. [CORJ access and formatting][c-api]; [serializer reads][c-serializer].

`onError(error, context)` observes **failure while reporting**, such as that getter's thrown Error; it is not the callback for the original tool failure. Context specifies stage, report path, and sometimes target field/property. The probe received the getter failure at `prop-access` and `as_json`, with report message null. A host that counts every `onError` call as a failed tool invocation double-counts secondary diagnostics failures. The default handler writes a warning; handler failure itself also triggers warning behavior. Consumers should decide where these secondary operational warnings belong. [Reporting error handling][c-api]; [maker tests][c-tests].

A catch block is not a deadline or a memory sandbox. A getter or formatter can spin forever, allocate heavily, mutate external state, or disclose information before returning. `Object.keys` must enumerate width before later traversal limits help. Child-source arrays can also have expensive enumeration; repeated references need not consume a new-node budget. `maxDepth` controls cause/error discovery, not an independently capped depth of arbitrary payloads inside `as_json`. The serializer is recursively implemented, and the whole-report limiter runs after discovery/field production. Output-size tests therefore do not establish bounded CPU, stack usage, or peak allocation for adversarial objects. For actual hostile code, isolation belongs outside the serializer. [Discovery][c-api]; [serializer traversal][c-serializer].

CORJ has no redaction option or separate public projection API. By default it captures a stack and enumerable fields that may contain tokens, request headers, paths, query text, or user content. A structured string can still contain malicious instructions; a schema says nothing about whether that content should influence an LLM's actions. The host must select/redact before exposure, preserve any trusted policy fields separately, and keep failure messages as data. “API error response” is a possible destination after application projection, not a safe default for raw reports. [Options and captured fields][c-api].

Semantic loss also exists without size truncation. Symbols/functions/undefined have no ordinary JSON form; non-finite numbers become null; the serializer's BigInt-to-number path can lose integer precision. Prototype behavior is not preserved. Circular payload references use a marker; this is not a general reversible object codec. Expected-value restoration can reconstruct format conventions, not the original live object or all its semantics. [Serializer conversion][c-serializer]; [serializer tests][c-serializer-tests].

### Harness example, combined usage, and claim ledger

The working-tree agent example wraps an async operation in `try/catch`, returns a discriminated `{ node, ok, value/error }` result, routes by `ok`, configures CORJ to 4,096 bytes, and asserts nested-cause/schema/size properties using fixture model clients. Its run ID lives outside the report. Thus the wrapper supplies the execution boundary and the routing decision; CORJ supplies the error representation. Those tests can protect a host contract without a paid model call, but do not evaluate model behavior or prove that CORJ caused the routing benefit. The same `ok` branch works with a minimal custom failure record. [Example publication path](https://github.com/dany-fedorov/caught-object-report-json/blob/main/examples/example-12-agent-harness.ts) — the example was local and unpublished when audited.

Using Application Exception with CORJ works structurally, with no dedicated integration. In the combined source probe, CORJ retained `_tag`, `id`, `timestamp`, `details`, and `name` in `as_json`; message remained reconstructible from the stack; the native cause became a child at `$.cause`. It did not promote the occurrence ID to a report reference, create a public code, or preserve Application Exception's symbol-backed message-rendering failure. A diagnostic `details.token` that App Exception redacted was exposed by CORJ. The source error's local class identity and guard were also not restored from JSON. These differences make adapter ownership concrete: choose one diagnostic representation, map stable fields explicitly, select public data, and retain run/tool/trace identifiers outside it. [Application Exception internals][a-internals]; [CORJ production][c-api].

| --- | --- | --- |
| One JSON-compatible report format for heterogeneous thrown values | Demonstrated mechanism | Field conversion, arbitrary-value fixtures and schema tests. |
| Bounded compact report and causal object references | Demonstrated mechanism | Size/graph implementation, invariant matrices and the combined probe. |
| Useful failure context at tool/graph-node boundaries | Conditional benefit | Host catches, retains relevant facts, supplies node/run identity and selects the destination. |

| Execution traces, replay, semantic recovery classification, secret filtering, safe hostile-object execution | Unsupported | Those mechanisms are absent from the package's public/runtime surface. |

### Worthwhile scenarios, wording and comparison plan

CORJ is plausibly worth adopting when SDKs throw heterogeneous objects, aggregate/shared causes matter, downstream systems want a consistent diagnostic schema, and hand-written serialization has repeatedly lost useful facts or exceeded payload caps. A common reusable serializer then removes recurring implementation work. It is less attractive when a harness only needs `{ ok: false, code, reference }`, an existing logger already serializes Error/cause appropriately, or Application Exception's diagnostic producer already meets the operational contract. Adding both report formats can instead increase schema knowledge and model-context overhead.

The new phrase “Structured JSON error reports for agentic development, LLM harnesses, and agent graphs” names plausible users but not a special mechanism. A stronger technical headline is “Bounded JSON reports for thrown values and nested causes.” Its harness-specific follow-up can say: “Use at tool or node catch boundaries; your host owns routing, public field selection, trace metadata and final context budgets.” “Modular reporting boundaries for context engineering” should identify the actual action—configuring captured child sources/depth and report size—and acknowledge that semantic selection/redaction is elsewhere. “Quick evals” should mean fixture assertions over failure reporting, not model-quality evaluation. [README publication path](https://github.com/dany-fedorov/caught-object-report-json/blob/main/README.md).

A fair experiment compares naïve native stringification, a purposeful record built from native Error/cause/AggregateError, the application's existing error serializer, and CORJ. Preserve identical required facts and host routing. Include plain errors, non-errors, shared/cyclic causes, SDK-shaped payloads, throwing accessors, Unicode, large values and secrets. Measure final bytes/tokens, schema validity, required-fact retention, accidental exposure, extraction failure rate, CPU and peak memory under controlled fixtures; isolate time-bounded adversarial probes in separate processes. For LLM utility, use fixed task failures and blinded diagnosis/recovery scoring with equivalent allowed facts. If a tiny explicit record gives equal outcomes with lower complexity, “agent harness benefit” is not demonstrated. If CORJ reduces serializer failures or preserves materially useful causes under the same budget, that is a defensible and narrower reason to adopt it.

## Verification record and reproducibility

Commands ran with `login:false` on Node `v24.20.0`, using installed dependencies, without rebuilding either repository:

| Repository / command | Outcome |
| --- | --- |
| Application Exception: `npm test -- --runInBand --silent` | 8 suites, 173 tests passed; 0 snapshots; Jest reported 1.834 s. |
| Application Exception: `npm run test:types` | `tsc -p ./tsconfig.types.json --noEmit` exited 0. |
| CORJ: `npm test -- --runInBand --silent` | 17 suites, 1,054 tests, 25 snapshots passed; Jest reported 5.951 s. A ts-jest warning says installed TypeScript 5.4.5 is outside its tested version range. |
| Source integration probe: `node --import ../application-exception/node_modules/tsx/dist/loader.mjs docs/research/error-boundary-harness-probe.ts`, from DI Bag | Exited 0; all explicit assertions passed. |

The first attempt to execute the original temporary probe through the `tsx` CLI failed before test execution because its IPC socket creation was denied (`listen EPERM`). Loading tsx through Node's import hook avoided that unnecessary socket and completed without escalation. The durable [source integration probe](error-boundary-harness-probe.ts) accompanies this report and imports sibling source checkouts through relative paths. It also asserts the exact reported getter counts, callback contexts and byte sizes. Reproducible assertions are: native Error stringification is `{}`; App Exception's cause is non-enumerable; missing required details survive an unchecked constructor call; nested details remain mutable; `_tag` is writable at runtime; CORJ retains enumerable App fields but loses renderer-failure metadata; CORJ exposes a token App diagnostics redact; getter invocation and reporting callbacks occur twice; report expansion exceeds its original byte cap; repeated aggregate causes reuse one child ID.

To reproduce, place `di-bag`, `application-exception`, and `caught-object-report-json` as sibling directories under any common parent. Use the two audited source commits listed at the beginning of this report. Install each source checkout's locked development dependencies with `npm ci` if they are not already present; the Application Exception checkout provides the `tsx` loader and its runtime dependencies. No build or installed package artifact is required. From the `di-bag` root run:

```sh
node --import ../application-exception/node_modules/tsx/dist/loader.mjs docs/research/error-boundary-harness-probe.ts
```

The audit used Node `v24.20.0`; repeat with that version for the closest comparison, especially for native Error behavior. This is an executable runtime probe, not a TypeScript typechecking command. Its intentional unchecked casts demonstrate runtime boundaries. It exits nonzero on an assertion failure and prints a JSON evidence summary after all assertions pass. It makes no external service requests. Later source or runtime versions can legitimately change these observations; rerun and assess failures before carrying the claims forward.

The full suites support the package contracts over their tested fixtures. Their pass counts are not independent security review, a performance benchmark, or evidence of LLM improvements. No model calls, deployment changes, commits, package installation, or network writes were performed.

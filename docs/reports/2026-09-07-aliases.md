# Checked aliases

Aliases are implemented through `e6c5bb6` on `feat/v0.1`.
`Builder.alias(destination, target)` and `ModuleBuilder.alias` accept checked
names or genuine tokens. A named target retains its exact inferred output; a token
target promises its declared service and may be supplied later. Each destination
retains its own name/token identity and compatibility obligations.

Resolution follows the target before allocating an attempt or choosing a cache
owner. An alias therefore preserves the canonical value, exact raw/native Promise,
transient multiplicity, dependency edges, readiness and cleanup. It has no separate
acquisition. Private module targets and renamed exports retain lexical routing.
Selected sharing follows the parent's effective graph; unshared aliases see child
target overrides. Fresh scopes and independent forks clear inherited sharing,
while explicitly re-sharing an alias retains parent routing.

Inspection exposes a frozen direct target binding ID/label in the effective owner
graph and canonical acquisition snapshots. Conservative metadata/frame types
avoid promising a stale target shape after replacement. The static graph retains
nominal requirements, completeness and lifetime checks through invariant builder
and module histories, reflected methods and emitted declarations.

## Design decisions

- Aliases are builder/module operations, preserving explicit canonical ownership;
  reusable transformable alias handles would require a separate ownership policy.
- Token targets promise their declared service, enabling forward/external aliases;
  callers wanting concrete implementation details must express those in the token.
- Inspection shows the direct relationship so alias chains remain visible; using
  only the terminal target would omit intermediate structure.
